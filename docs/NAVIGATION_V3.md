# FarmAssist: Navigation v3

Цей документ фіксує фактичні маршрути й доповнюється кумулятивно у PR-D → PR-E → PR-F. Серверний API, OpenAPI-контракт, пошук v2, медичні застереження, фармаконагляд, серверна історія й операторські сторінки не змінюються.

## PR-D — консолідація маршрутів і меню

Канонічна головна — пошук на `/`. Перевірка відпуску є самостійним конвеєром, тому лишається на `/dispense` і доступна великим ярликом під пошуком. Канонічна картка реєстрової позиції — `/products/:productId`.

### Таблиця редиректів

| Старий URL                     | Новий URL                                              | Примітка                                                                                           |
| ------------------------------ | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| `/search?...`                  | `/?...`                                                | Усі query-параметри, включно з `q`, зберігаються.                                                  |
| `/instructions/:productId?...` | `/products/:productId?...&tab=instruction#instruction` | Наявний `tab` і hash мають пріоритет; реєстраційний номер зберігається.                            |
| `/drug/:id`                    | `/search?q=<торгова назва>`                            | Назва резолвиться наявним legacy API; при невідомому ID — `/search`. Новий ID-мапінг не будується. |
| `/analogs/:id`                 | `/search?q=<торгова назва>`                            | Той самий безпечний legacy-резолвер; аналоги надалі відкриватимуться з ProductCard.                |
| `/analogs`                     | `/`                                                    | Без вибраної позиції.                                                                              |
| `/ai`, `/ai-reference`         | `/`                                                    | AI-довідка переноситься в ProductCard у PR-E і не викликається автоматично.                        |
| `/scan`                        | `/?scan=1`                                             | Відкриває OCR-діалог; розпізнаний текст лише підставляється в пошук.                               |

### Основна навігація

На мобільному та десктопі рівно три пункти:

1. **Пошук** — `/`.
2. **Взаємодії** — `/interactions`.
3. **Збережене** — `/history` (`/favorites` стане вкладкою у PR-E).

`/regulatory-radar`, `/about`, `/dispense`, `/instruction-search`, `/compare`, `/pharmacovigilance` та операторські маршрути лишаються доступними прямими URL, але не входять до основного меню. Постійні посилання на регуляторні оновлення й сторінку «Про застосунок» розміщені у футері головної.

### Інваріанти OCR

- OCR-текст не є довіреною реєстровою ідентичністю.
- Результат потрапляє в те саме поле `q`, тому проходить через наявний `useCatalogClientNormalizedSearch` → `normalizeAndSearch`.
- Автоматичного переходу на ProductCard немає.
- За недоступного AI/OCR користувач отримує пояснення й повертається до ручного поля.

## PR-E — ProductCard як картка-хаб

Канонічний `/products/:productId` має три вкладки, керовані параметром `tab`:

1. **Профіль** — точна реєстрова ідентичність, статуси, госпітальні цитати, переліки/ціна та свіжість джерел.
2. **Аналоги** — lazy-компонент із клієнтського реєстрового індексу. Показуються лише позиції з тією самою МНН; повний збіг форми й дозування відділений від часткового. Терапевтичні аналоги без окремої перевіреної бази не формуються.

   Коли реєстр зберігає МНН позиції як загальну позначку без деталізованого складу (наприклад «Comb drug» для комбінованих препаратів), збіг за таким рядком не вважається аналогією: цей рядок буквально повторюється в сотнях непов'язаних позицій (`isNonSpecificInn` у `lib/catalog-index`). Замість нього ідентичністю стає перелік діючих речовин із Національного каталогу цін МОЗ — структуроване поле «МНН» цього каталогу, приєднане за реєстраційним номером. Компоненти нормалізуються, дедуплікуються й сортуються (`catalogCompositionKey`), тож той самий склад, записаний в іншому порядку, дає той самий ключ; роздільниками є лише `+` і `;`, бо кома трапляється всередині назви речовини («2,4-дихлорбензиловий спирт»). Ключ потрапляє сьомим полем у рядок клієнтського індексу й заповнюється **тільки** для позицій із позначкою-заглушкою, тому справжня МНН ніколи не підміняється каталогом цін. Вкладка явно позначає, що підбір зроблено за складом і що джерело складу — каталог цін МОЗ, а не ДРЛЗ. Якщо структурованого складу немає, показується пояснення без списку аналогів.

3. **Інструкція** — структуровані офіційні розділи, пошук у них і перехід до загального пошуку в інструкціях.

`?tab=profile` є безпечним значенням за замовчуванням, `?tab=analogs` і `?tab=instruction#instruction` можна відкривати прямим URL. Верхній блок точної позиції лишається спільним для всіх вкладок.

### Контекстні дії картки

- AI-довідка завантажується lazy і викликає API тільки після явного натискання. У межах поточної браузерної сесії результат і незавершений запит кешуються за `productId`.
- Фармаконагляд зберігає чинний workflow та отримує `productId` і реєстраційний номер із картки.
- Кошик взаємодій зберігає до п’яти точних реєстрових позицій у `localStorage`; його глобальний індикатор веде на `/interactions`. Додавання, вилучення й очищення синхронізовані з екраном перевірки.
- Порівняння лишається контекстною дією картки, а не пунктом основного меню.

### Збережене і legacy-сторінки

`/history` об’єднує вкладки **Історія** та **Обране**. `/favorites?...` редиректить на `/history?...&tab=favorites` зі збереженням інших параметрів. Старі компоненти `favorites`, `analogs` і `ai-reference` видалені з білда; їхні URL-контракти підтримують редиректи з PR-D.

## PR-F — швидкий доступ і миттєве відкриття картки

### Швидкі картки на головній

Під полем пошуку показуються до п’яти конкретних реєстрових карток: спочатку обрані, потім останні переглянуті без дублікатів. Чіпи ведуть безпосередньо на `/products/:productId`; legacy-позиції, для яких потрібен проміжний пошук, у швидкий ряд не потрапляють. У «Збереженому» локальна історія карток зберігається окремо від наявної серверної історії дій.

### Попередня картка з клієнтського індексу

Під час очікування API верхній блок ProductCard може одразу показати лише шість наявних у клієнтському індексі полів: `productId`, реєстраційний номер, торгову назву, МНН, форму й дозування. Категорія відпуску, чинність реєстрації, заборони та інші медичні/регуляторні статуси лишаються скелетонами. Після відповіді API попередній об’єкт повністю замінюється серверною карткою — поля не мерджаться.

### Оновлення й глобальний доступ

- На головній з’являється банер тільки для ще не переглянутої версії перевіреного регуляторного знімка. Версія визначається датою останнього документа і кількістю записів, а не часом щоденної перевірки. Відкриття `/regulatory-radar` або закриття банера позначає цю версію переглянутою.
- На внутрішніх екранах є компактний пошук; `/` на десктопі фокусує його, якщо користувач не вводить текст в іншому полі. `Esc` очищає поле, `↑`/`↓` пересувають вибір, `Enter` відкриває явно вибрану картку. Точні `primary`-результати й виправлені `suggested`-підказки візуально розділені. На головній зберігається велике основне поле без дублювання.
- PWA відкривається на канонічному `/`. Системні ярлики ведуть на `/dispense` («Перевірка відпуску») і `/interactions` («Перевірка взаємодій»).

### Межі PR-F

Пошук v2 та його `primary`/`suggested` контракт, OpenAPI, серверні маршрути, медичні застереження, фармаконагляд, операторські сторінки й Workbox-стратегія не змінюються. У manifest змінені лише стартовий URL, ярлики та їхні локальні іконки.
